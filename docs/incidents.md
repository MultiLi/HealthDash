## 一、数据完整性

### 1. 报告自称「覆盖全天」，实际截止 23:29（2026-09-09）

报告头部写着完整覆盖，`wellnessEndTimeLocal` 却是 23:29。关键词搜「非终版」「截止」全漏。

**根因**：用报告文本判断数据完整性。
**防线**：一律读 `data/raw/*.json` 的 `usersummary_daily.wellnessEndTimeLocal`，落在次日 00:00 才算完整。`canonical.coverage.cutoff_min` 是唯一入口。

### 2. 半天账把机制归因带反（2026-09-12）

当天报告基于 1636 步判「活动不足导致恢复差」，补全后实为 **16444 步**。四份报告返工。

**根因**：引用相邻日数字前没验完整性。
**防线**：`data_gate.py` 是「报告能不能开写」的唯一判据；截断日的聚合值不参与周/月计算（但日尺度保留值）。

### 3. 一天出三版报告（2026-09-07）

21:56 出 5887 步版、22:12 再出一版、23:30 才拿到全天 9678 步。前两版作废。

**根因**：没有「日内不产结论性报告」的纪律。
**防线**：红黄绿只由 23:30 终版出。`slot.py` 账本阻止重复派发。

### 4. 空占位响应打挂整个窗口（2026-10-08）

未佩戴日，Garmin 仍返回**结构完整、值为空**的模板（`totalSteps` 为 null、`stressValuesArray` 长度 0、`wellnessEndTimeLocal` 为空）。`adapters/garmin_cn.py::_day_anchor` 抛 `AttributeError`，**一个空日让整个窗口的 fact_pack 全挂**。

**根因**：把「文件在不在」当判据，把「字段形态」当正常。
**防线**：`_day_anchor` 已加 guard。连续空日出现时先跑一次 `fact_pack` 确认不崩。

### 5. 截断日永远截断（2026-10-13 ~ 10-16）

raw 一旦落盘就不重拉，被截断的历史日只能靠人工 `--force` 补完。

**根因**：幂等策略过强——「已落盘」被当成「已完整」。
**防线**：`collect.py` 第 ② 步自动回补：`data_gate` 判 partial 的才碰，完整日不动。

## 二、口径与判定

### 6. 久坐被算成 22 小时 36 分（2026-10-08）

无睡眠记录的日子，久坐分母退化成 ≈1440 分钟。

**根因**：`awake_den = 1440 − 睡眠 − 清醒 − 午睡`，睡眠缺失时分母不收缩。
**判据**：把三个活动分档加总，接近 1439min 就是分母伪影（10-07：1356+78.6+4.4 = 1439）。
**防线**：无睡眠记录日的久坐**不可引用、不可与长期序列（14h45m–16h18m）并列比较**。

### 7. 逐时层覆盖不完整但被当成可信（2026-10-08）

10-07 逐时网格合计 7291 步，`usersummary` 实测 11379；压力分档只覆盖 402min。

**根因**：以为「有数据 = 数据可信」。
**防线**：必做两个交叉校验——网格合计 vs usersummary 总量、分档合计 vs 清醒时长。不齐就降权，**总量一律以 usersummary 为准**。

### 8. `--force` 低估累计字段（2026-10-17 / 10-18）

截断日补全后久坐普遍上抬 3–5 小时，终值稳定在 14h45m–15h12m。

**防线**：报告里出现「久坐 10–11 小时」量级时，**先怀疑数据截断，而不是身体变好**。

### 9. 步数双尺子（2026-10-25，待定）

`units.judge` 与主页用 `steps_goal`=10000，断言层用 `steps_good`=8000。后果：9000 步那天主页显示「未达标」、报告却不吭声。

**状态**：已具名声明，仍待决定二选一或分场景说明。见 `docs/decisions.md` D1。

### 10. 代码总评红，报告全写黄（2026-10-25）

30 份有报告的日子里，**8 天代码总评为红**（09-03/04/13/14/17、10-14/20/24），而 32 份历史报告**无一篇红灯**。触发源集中在 `sleep.duration.very_short`、`activity.steps.severe`、`cross.sleep_debt_autonomic`。

**根因**：「总评 = 最差维度」这条规则，LLM 判读时**从未真正执行过**，对红有系统性回避。
**防线**：`verify_judgment.py` 现在能自动抓出（10-24 报错「规则档红 / summary 写黄」）。允许降档但必须写 `downgrade_reason`。

### 11. 覆盖不足时仍给「明显变化」（2026-10-25）

近 28/90 天窗覆盖 50% 时，`delta` 照旧输出「明显变化 / 在误差内」——把「缺数据」算成了「变了」。

**防线**：`units.delta` 加覆盖率门禁，coverage < 门槛直接判 `insufficient`。

## 三、归因

### 12. 「深睡跟体力支出走」被推翻（2026-10-17）

早上基于 4 个样本提出该假设，当晚被推翻：`facts.target_day.sleep` 是**当日凌晨结束的那一觉**，负荷来自前一日，**配对方向反了**。按正确对齐（负荷日 → 次晨深睡）后不单调（84 / 83 / 62 / 60）。

**残留**：只剩「负荷信号消散后深睡回落」的弱版本（n=4、提示级）。
**防线条目**：报告里不要写「深睡低 = 当天没运动」，也不要写「深睡不足 = 睡太晚」。

### 13. 「晚睡 → REM 必崩」不成立（2026-10-22 vs 10-23）

两晚都是凌晨 3 点后入睡（03:33 / 03:12），REM 却是 **9.7% vs 28.4%**。决定 REM 的是**起床时刻 + 睡眠连续性**（10-22 被 09:43 起床截断；10-23 推到 09:37、清醒仅 1min），不是入睡钟点。

**防线条目**：别再写「三点睡所以 REM 低」。

### 14. 心率峰值两层口径差 19bpm（2026-10-18）

`activities[].max_hr`（活动记录）=132，`hr_hourly` 的 hourly max（2min 采样层）=113。

**防线**：活动峰值用活动记录、Z2/运动窗用采样层，并列时必须写清口径。

### 15. Z2 三种失败形态被混为一谈（2026-10-22）

① 配速低一档（10-18：均 97、整段 Z1）；② 到 Z2 就收工（10-21：进过 110–117）；③ **全天没有一个采样样本到 109**（10-22：629 个样本峰值仅 103）。

**防线**：判据是「样本里有没有一个 ≥109」，别一律归到「配速」。

### 16. 跨日归因前没补齐相邻日（2026-09-10）

补 09-10 逐时心率后，09-11 的 HRV 崩塌从「工作应激」改判为「连续两晚夜走的急性负荷堆积」。

**防线**：判读相邻日形态时，把同时段的小时级 步数/压力/心率 做成多日并排表——「单调下行 vs 平坦不降」只看当日看不出来。

## 四、工程

### 17. 兜底脚本覆盖了终版报告（2026-10-25）

`compose.py --write --force` 把 10-24 的 LLM 报告覆盖成骨架版，`body_brief.json` 里的 judgment 也已被前一次 fact_pack 抹掉。**唯一载体是会话转录**（`~/.workbuddy/projects/.../*.jsonl`），逐字节恢复。

**根因**：兜底脚本拥有和正式产出同等的写权限。
**防线**：写路径拆两级——`--write` 只写 `.skeleton.md`，`--as-final` 才碰正式报告且需 `--force`。**兜底脚本不该有随手覆盖终版的权限。**

### 18. GitHub 的 `.gitignore` 模板吃掉前端源码（2026-09-16）

GitHub 生成的 Python 模板含 `/site` 一行（mkdocs 产物目录），把本项目的前端源码目录整个忽略。

**防线**：已移除并在 `.gitignore` 头部注明。改 ignore 规则时别加回来。

### 19. 后台起服务进程随命令退出消失（2026-09-16）

`(cmd &)` 子 shell 起的 server 随命令结束被回收，截图一律连不上。

**防线**：用工具的后台模式起常驻服务，或同一条命令里「起 → 截图 → kill」。

### 20. 交互探针永不返回（2026-09-16）

给无头 Chrome 传 `--user-data-dir=<新建目录>` 会让它卡死，症状是「所有用例 HUNG」。

**判据**：**连基线都 HUNG 就是工具坏了**，不是用例问题。默认复用默认 profile + `--incognito`。

### 21. 把「设计使然」当缺陷（2026-10-18）

`assetver` 每次构建重写 10 个 js 曾被列为技术债。实际是必要的：`data.js` 里嵌着 `index.json?b=<token>`，数据变而这个 URL 不变就会被边缘缓存钉死。改掉它会破坏缓存策略。

**教训**：判「这是 bug」之前，先确认它在防什么。

### 22. SSH 主机键过期被误判为攻击（2026-10-25）

`known_hosts` 第 1 行是 GitHub 2024-03 轮换前的旧 RSA 键，报 `REMOTE HOST IDENTIFICATION HAS CHANGED`。

**防线**：先用 `api.github.com/meta` 核对官方三把主机键指纹，与 `keyscan` 结果一致再 `ssh-keygen -R` 重写。**确认陈旧而非 MITM 才动手。**

### 23. 一个空日打挂整个窗口（2026-10-08）

见第 4 条。单独列出是因为它的爆炸半径最大：**单日数据问题会把整批 fact_pack 全部打挂**，报错位置离根因很远。

### 24. 个人健康数据被推到公开仓库（2026-10-31 发现）

`github.com/MultiLi/HealthDash` 是 **public** 仓库，且已推送。里面含：
`MEMORY.md`（体重、体成分、体脂率、骨骼肌）、`notes/inbody_baseline_2026-10-18.md`、
`notes/frontend-audit-2026-09-16/` 14 张**带真实数值的页面截图**、
`.workbuddy/memory/` 全部每日健康日志与自动化执行记忆、
以及 git 历史里的 `notes/events.jsonl`（21 行健康事件原文：体重、加班作息、情绪）。

**根因不是 `.gitignore` 写漏了一行，是结构问题**：数据散在 7 个位置
（`reports/`、`daily_log.jsonl`、`notes/events.jsonl`、`data/raw/`、`data/inbody/`、
`data/state/health.db`、`site/.data/`），每处都要单独加一条 ignore 规则。
规则越多越容易漏，而漏一次的代价是**数据已经在公网上，撤不回来**。
更隐蔽的是：文件后来被 ignore 了，**但已跟踪的文件不会自动退出索引**，
`git add -A` 会把「untracked 但未被忽略」的 `MEMORY.md` 再送进去一次。

**防线（三道，缺一不可）**：
1. **结构**：全部个人数据收进 `data/` 单根，`.gitignore` 一行 `data/*` 封死。
   新增数据目录不需要改规则，天然不入库。
2. **内容扫描**：`tools/guard_no_data.py` 扫已跟踪文件的**内容**（不限路径），
   命中「体重 + 具体公斤数」「体脂率 + 百分比」「HRV + 具体毫秒数」这类实测值
   即报错并 exit 1。这条规则连本文档也管——写事故复盘时引用真实数字会被它拦下，
   只能写成中性描述。
   `.gitignore` 只能拦你想到的位置，内容扫描才能发现"换个文件名又漏了"。
3. **归档**：`data/` 整体不备份到 git，改由 `tools/backup_health.py` 加密备份。

**历史清理的诚实结论**：用 `filter-branch` 重写全部 16 个提交并强推之后，
当前 HEAD 里的敏感路径已 404，**但旧 commit 仍可通过 API 读到**
（`contents/notes/events.jsonl?ref=<旧SHA>` 返回 200 与完整 21 行）。
GitHub 会保留不可达对象，强推改变不了这一点。要彻底消除只有两条路：
联系 GitHub Support 请求清理不可达对象，或删库重建。**「强推过了」不等于「清干净了」，
这个区别必须记住。**

**处置：2026-10-31 Sir 决定接受该残留，不做进一步清理**（判断依据：仓库无 star/fork、
无法被检索到具体 SHA、残留内容为 9 月早期记录）。**这是「已知并接受」，不是「已解决」**——
所以留档在此。今后若有人（或 agent）重新发现旧 commit 可读，不要当成新事故处理，
也不要再提议删库；除非 Sir 自己改变主意。相关依据见 `docs/decisions.md` D-23。

## 增补规则

- 新事故**必须带日期和实证数字**，否则无法在 `golden.json` 里复现。
- 如果一条事故可以写成断言，就写成断言进 `data/tests/golden.json`，然后在本文留一行指针。
- 不要在这里写「应该注意」这类无法验证的劝告——那种东西写完就没人看了。
